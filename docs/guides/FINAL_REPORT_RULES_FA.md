# قاعدهٔ دائمی گزارش نهایی و پیشرفت

این قاعده از [AGENTS.md](../../AGENTS.md) منتقل شده و همان اعتبار الزام‌آور را دارد.

## گزارش نهایی فارسی

پس از **هر وظیفهٔ Codex**، گزارش نهایی خطاب به کاربر باید کاملاً به فارسی روشن، حرفه‌ای و قابل فهم نوشته شود. شناسه‌های فنی انگلیسی، نام فایل، symbol کد، نام SQL، مسیر API، فرمان و مقدار ماشین‌خوان دست‌نخورده بمانند. متن مختلط RTL/LTR خوانا باشد. این الزام فقط به گزارش پایان checkpoint محدود نیست و کار Git، مستندات و رفع اشکال را نیز شامل می‌شود.

گزارش باید متناسب با تغییر، موارد زیر را دقیق بیان کند؛ مورد بدون تغییر را کوتاه اعلام یا در صورت بی‌ارتباط‌بودن حذف کنید:

۱. چه چیزی پیاده‌سازی یا انجام شد.
۲. چه فایل‌هایی ساخته شدند.
۳. چه فایل‌هایی تغییر کردند.
۴. چه endpointهای API اضافه یا اصلاح شدند.
۵. چه جدول‌ها یا migrationهای SQL Server اضافه یا اصلاح شدند.
۶. کدام آزمون‌ها واقعاً اجرا شدند و نتیجهٔ دقیق آن‌ها چه بود.
۷. نتیجهٔ واقعی build و اجرای برنامه چه بود.
۸. خطاها، warningها و مسائل حل‌نشده چه هستند.
۹. چه نگرانی امنیتی باقی مانده است.
۱۰. SHA واقعی commitها و نتیجهٔ تأییدشدهٔ push چیست.
۱۱. پروژه اکنون در چه phase/checkpoint است.
۱۲. چه کارهایی باقی مانده‌اند.
۱۳. checkpoint پیشنهادی بعدی چیست و چه مجوز یا وابستگی لازم دارد.

پس از **هر checkpoint**، درصد قبلی، سهم کسب‌شده با شاهد پذیرش، درصد جدید، کار باقی‌مانده و برآورد مشروطِ درصد پس از checkpoint بعدی را با مبنای محاسبه در گزارش نهایی و PLAN ثبت کنید. وزن‌های پایه: `0=3%`، `1=6%`، `1.5=3%`، `2=12%`، `3=12%`، `4=10%`، `5=8%`، `6=16%`، `7=8%`، `8=12%`، `9=10%`؛ مجموع `100%`. پیش از 2A/2B برابر `12%` بود؛ سهم آن‌ها `3`، 2C برابر `2`، 2D برابر `2` و طرح پذیرفتنی 2E طبق دامنهٔ صریح مالک برابر `1` پذیرش متصل 2F در 2026-11-07 برابر `2` و 2G (migration/rollback) برابر `2` است؛ فعلی `24%`. نگهداری صرف مستندات و بررسی ناموفق gate امتیاز ندارند؛ سهم 2E فقط متعلق به طراحی مصوب همین مرحله است، نه اجرای Info. برای کار ناتمام امتیاز ندهید؛ طراحی را اجرای SQL/آمادگی Production معرفی نکنید. تغییر وزن فقط با توضیح روشنِ تغییر دامنه و ثبت در PLAN مجاز است.

هرگز موفقیت عملیات را بدون بررسی اعلام نکنید. «اقدام به push»، «push موفق»، «تطبیق HEAD محلی/remote» و «قابل مشاهده‌بودن فایل در GitHub» ادعاهای جدا هستند و هرکدام شاهد خودش را می‌خواهد. اجرای موفق آزمون قبلی را به‌عنوان اجرای تازه معرفی نکنید. [گزارش همگام‌سازی GitHub](../GITHUB_SYNC_FA.md) وضعیت واقعی ارسال را ثبت می‌کند.
