# قواعد کسب‌وکار

این سند مرجع قواعد قطعی است؛ جزئیات سیاست‌های هنوز تصویب‌نشده در [OPEN_DECISIONS_FA.md](OPEN_DECISIONS_FA.md) قرار دارد.

## مالکیت و تکمیل اطلاعات

کد معرفی متعلق به درخواست بیمه است. مالکیت از زنجیرهٔ معتبر `Brokerage → SourceRequest → SourceCustomer → TrustedMobile` حاصل می‌شود و فقط پس از OTP نشست صادر می‌شود. داشتن کد، HMAC، شناسهٔ بازدید یا رسید به‌تنهایی مجوز نیست. هر نشست مشتری فقط همان درخواست را پوشش می‌دهد؛ برای درخواست دوم احراز زمینهٔ همان درخواست لازم است.

مقدار معتبر مبدأ با `source=Brokerage` برمی‌گردد و در UI و Backend فقط‌خواندنی است. نبود مقدار، `null` و `status=Missing` است؛ مشتری آن را با اعتبارسنجی تکمیل می‌کند و منشأ `Manual` می‌شود. مقدار نامعتبر مبدأ `InvalidSource` است؛ خودکار به مقدار ساختگی یا قابل‌ویرایش تبدیل نمی‌شود. سیاست رفع این وضعیت باید تصویب شود. صفر فقط برای mapping صریح همان فیلد مفقود است. کیلومتر صفر، دقت صفر واقعی یا مختصات صفر را سراسری حذف نکنید.

Backend فهرست مجاز فیلدهای دستی را از snapshot معتبر خودش می‌سازد؛ `readOnly` یا `source` ارسالی مشتری قابل اعتماد نیست. تلاش برای تغییر مقدار trusted، خطای فیلدی می‌دهد و تغییر جزئی ذخیره نمی‌شود. مغایرت، گزارش جداست و حق بازنویسی master ایجاد نمی‌کند. دادهٔ نهایی، منشأ، نسخه و زمان تأیید در `BAZDIDInfo` ذخیره می‌شوند.

## مدارک بازدید جدید

| عکس ثابت | `requirementId` |
|---|---|
| جلو ۴۵ درجه راست | `front-45-right` |
| عقب ۴۵ درجه راست | `back-45-right` |
| جلو ۴۵ درجه چپ | `front-45-left` |
| عقب ۴۵ درجه چپ | `back-45-left` |
| کیلومترشمار روشن | `odometer-on` |
| کابین سمت راننده | `driver-interior` |
| محفظهٔ موتور | `engine-bay` |
| سقف | `car-roof` |
| پلاک جلو | `front-plate` |
| پلاک عقب | `rear-plate` |

جایگاه یازدهم `spec-plate` و گروه `vehicle-identification` است. دقیقاً یک `alternativeId` لازم دارد:

| مقدار | محل |
|---|---|
| `pillar` | ستون درِ راننده |
| `engine` | محفظهٔ موتور/دیوارهٔ آتش |
| `seat` | زیر صندلی راننده یا شاگرد |
| `windshield` | لبهٔ شیشهٔ جلو |

سه گزینهٔ انتخاب‌نشده مفقود نیستند. عکس `engine` جای `engine-bay` را نمی‌گیرد. صرف شمار ۱۱ کافی نیست؛ عضویت هر مدرک در الزام و قالب پین‌شده، یکتایی جایگاه و گزینهٔ واقعی نسخه بررسی می‌شود.

یک ویدیوی الزامی `video-360` نیز لازم است؛ در قالب فعلی ۱۲ **فایل** داریم، اما ۱۱ **عکس**. کیلومتر عددی فایل نیست؛ مقدار صحیح نامنفی جداگانه است. محدودهٔ قابل انتقال فعلی JavaScript تا `9007199254740991` است؛ سقف واقعی کسب‌وکار هنوز باز است. هیچ تشخیص خودکار پوشش واقعی ۳۶۰، کیفیت نور یا صحت GPS ادعا نمی‌شود.

قالب تازه `body-image-guided`، `templateVersion=2` و `photoPolicyVersion=2` است. بازدید تاریخی نسخهٔ ۱ با ۱۲ عکس مستقل، قالب و هویت مدرک خود را حفظ می‌کند. نام logical الزام با شناسهٔ SQL یا انتخاب guide یکی نیست. تغییر guide، مدرک پذیرفته‌شده را بازبرچسب‌گذاری نمی‌کند.

## پیش‌نیاز ارسال و چرخهٔ عمر

قبل از ارسال: رضایت نسخه‌دار، موقعیت معتبر و تأییدشده، اطلاعات کامل و معتبر، کیلومتر، تمام جایگاه‌های لازم و رسید پایدار فایل **همان نسخه‌های هدف** لازم‌اند. Blob محلی، queue، فایل در حال انتقال یا جایگزین تأییدنشده رسید سرور نیست. `uploaded/processing` با تأیید Reviewer برابر نیست؛ انتشار فایل مستلزم اتمام کنترل‌های امنیتی دریافت است.

Checkpointهای مشتری، فقط `DRAFT → UPLOAD_PENDING → SUBMITTED` و بازگشت به DRAFT پیش از submit را اجرا می‌کنند. summary از وضعیت واقعی سرور مشتق می‌شود، نه ادعای completion مرورگر. ارسال با کنترل نسخه، قفل داده و ثبت snapshot/receipt/history/audit در یک transaction انجام می‌شود. retry همان کلید، همان رسید را می‌دهد؛ GET هیچ تلاش تازه‌ای نمی‌سازد.

چرخهٔ آینده به ترتیب `UNDER_REVIEW`، `CHANGES_REQUESTED`، `REJECTED`، `REVIEW_APPROVED`، `FORWARD_PENDING`، `FORWARD_FAILED` و `FORWARDED` را اضافه می‌کند. اصلاح جزئی فقط اقلام درخواست‌شده را باز می‌کند؛ اصل و سابقه می‌مانند. رد کامل تلاش قبلی را حفظ می‌کند؛ تلاش تازه با شناسه و پوشهٔ تازه، بدون کپی رضایت/کیلومتر/رسانه ایجاد می‌شود. هر ردیف `BAZDIDInspections` یک تلاش است؛ جدول تلاش موازی لازم نیست.

تأیید کلی کارشناس مستقل از تصمیم هر مدرک است. فقط رسید معتبر مقصد برای نسخهٔ مشخص، `FORWARDED` ایجاد می‌کند. نقش مدیر به‌تنهایی حق تصمیم کارشناسی نمی‌دهد. یادداشت داخلی وارد پاسخ مشتری نمی‌شود. این قابلیت‌ها برای فاز بعد طراحی شده‌اند و اکنون فعال نیستند.

## مرز داده و فایل

Session فقط احراز و زمینهٔ موقت است. دادهٔ بازدید مستقل از restart، logout و انقضای Session باقی می‌ماند. SQL فقط metadata و snapshot JSON تجاری دارد؛ عکس و ویدیو خارج از webroot هستند. حذف یا جایگزینی فایل نباید رسید قبلی را نامعتبر یا تاریخچه را پاک کند.
